# libavoid C++ vs Rust Port: Implementation Parity Audit

**Date**: 2024-11-24
**Auditor**: Claude Code
**Scope**: Full algorithmic comparison of adaptagrams/cola/libavoid (C++) vs libavoid-rust (Rust)

---

## Executive Summary

The Rust port is a **functional implementation** that captures the core algorithms of libavoid but with **significant simplifications** in several areas. The port correctly implements the fundamental routing pipeline but deviates from the C++ implementation in ways that may affect edge cases, performance characteristics, and route quality in complex scenarios.

### Overall Assessment

| Category | Parity Level | Notes |
|----------|--------------|-------|
| Core Architecture | **High** | Same transaction-based design |
| Visibility Graph | **Medium** | Simplified sweep algorithm |
| A* Pathfinding | **Medium-High** | Similar but simpler cost model |
| Orthogonal Routing | **Medium** | Different approach (grid-based A* vs visibility graph) |
| VPSC Solver | **Medium** | Simplified block-based solving |
| Nudging | **Medium** | Similar VPSC approach but different segment classification |
| Hyperedge Routing | **Low-Medium** | Basic implementation present |

## 1. Visibility Graph Implementation

### C++ Implementation (`visibility.cpp`)

The C++ implementation uses **Lee's Visibility Sweep Algorithm** (Lee 1978) with a proper sweepline data structure:

```cpp
// Key structures
class PointPair {
    VertInf *vInf;
    double angle;      // Rotational angle from center
    double distance;   // Distance from center
};

class EdgePair {
    VertInf *vInf1, *vInf2;  // Edge endpoints
    double angleDist;        // Distance along current ray
};
```

**Algorithm characteristics**:
- Uses sorted vertex set by angle for sweep ordering
- Maintains active edge list (`SweepEdgeList`) for blocking edges
- Proper handling of shape containment via `router->contains[pID]`
- Visibility cones checked via `inValidRegion()` for shape corners
- O(n log n) complexity with proper sweepline

### Rust Implementation (`visibility.rs`)

The Rust implementation has **two modes**:

1. **Naive O(n²) visibility** (`compute_vertex_visibility`):
   - Simple pairwise visibility check
   - Uses `segment_intersects_polygon_interior()` for each pair
   - No sweepline optimization

2. **Sweep algorithm** (`compute_vertex_visibility_sweep`):
   - Attempts Lee's algorithm but **simplified**
   - Missing proper sweepline tree data structure (uses `Vec` instead of balanced tree)
   - Edge updates in `sweep_update_active_edges` are simplified

### Key Differences

| Aspect | C++ | Rust |
|--------|-----|------|
| Sweepline structure | `SweepEdgeList` (sorted list) | `Vec<SweepEdge>` (unsorted) |
| Angle computation | `rotationalAngle()` with proper quadrant handling | Basic `atan2` |
| Containment handling | `router->contains[pID]` map | Not implemented |
| Visibility cones | `inValidRegion()` check | Not implemented |
| Edge event handling | Proper add/remove with `vecDir` | Simplified |

### Impact

- **Correctness**: May produce incorrect visibility for endpoints inside shapes
- **Performance**: Rust falls back to O(n²) in practice
- **Route Quality**: Routes may differ near obstacle corners

## 2. A* Pathfinding

### C++ Implementation (`makepath.cpp`)

```cpp
class ANode {
    VertInf* inf;
    double g;           // Cost from source
    double h;           // Heuristic to target
    double f;           // f = g + h
    int timeStamp;      // Deterministic tie-breaker
};

class AStarPathPrivate {
    std::vector<ANode*> m_available_nodes;  // Block allocator (5000 nodes/block)
    std::vector<VertInf*> m_cost_targets;   // Multiple targets for heuristic
};
```

**Key features**:
- **Block allocation** for memory efficiency (5000 ANodes per block)
- **Timestamp-based tie-breaking** for deterministic routing
- **Multiple cost targets** for asymmetric heuristics
- **Penalty application** during edge traversal:
  - `segmentPenalty`: Per-unit-length cost
  - `anglePenalty`: Bend cost (angle-proportional)
  - `crossingPenalty`: Experimental crossing cost
  - `portDirectionPenalty`: Visibility cone violations
  - `reverseDirectionPenalty`: Away from destination

### Rust Implementation (`graph.rs`)

```rust
pub struct SearchState {
    pub g_score: f64,
    pub f_score: f64,
    pub came_from: Option<VertexId>,
    pub came_from_direction: Option<Point>,
    pub generation: u32,  // Reuse without clearing
}
```

**Key features**:
- Standard A* with BinaryHeap
- Generation-based state reuse (clever optimization)
- Simpler cost model

### Key Differences

| Aspect | C++ | Rust |
|--------|-----|------|
| Memory allocation | Block allocator | Standard HashMap |
| Tie-breaking | Timestamp field | None (non-deterministic) |
| Heuristic targets | Multiple | Single |
| Penalty system | 6+ penalty types | Simplified (segment, bend, crossing) |
| Port directions | Full `inValidRegion` check | Direction flags only |

### Impact

- **Determinism**: Rust routes may vary between runs for equal-cost paths
- **Route Quality**: Fewer penalty types means less aesthetic optimization
- **Performance**: No block allocation means more allocations

## 3. Orthogonal Routing

### C++ Implementation (`orthogonal.cpp`, 3259 lines)

The C++ implementation uses a **comprehensive scanline-based approach**:

1. **Orthogonal Visibility Graph Generation**:
   - Two-pass scanline sweep (X then Y)
   - Creates dummy vertices on shape edges
   - Builds `visOrthogGraph` separate from polyline graph

2. **Route Search**:
   - A* on the orthogonal visibility graph
   - Proper handling of connection pin directions

3. **Nudging** (detailed below)

### Rust Implementation (`orthogonal.rs`, 883 lines)

The Rust implementation uses a **fundamentally different approach**:

1. **Simple L-shaped paths first**:
   ```rust
   fn route_h_v_simple(&self, start, end, obstacles) -> Option<Polygon>
   fn route_v_h_simple(&self, start, end, obstacles) -> Option<Polygon>
   ```

2. **Grid-based A*** fallback:
   - Implicit grid at `GRID_RESOLUTION = 1.0`
   - Direction-encoded node IDs
   - Manhattan distance heuristic

### Key Differences

| Aspect | C++ | Rust |
|--------|-----|------|
| Primary approach | Visibility graph | L-shape + Grid A* |
| Graph type | Explicit orthogonal visibility graph | Implicit grid |
| Grid resolution | Continuous | Fixed 1.0 unit |
| Direction handling | Connection pins + visibility cones | ConnDirFlags |
| Complexity | O(n log n) visibility + A* | O(n²) grid A* |

### Impact

- **Route Quality**: Grid-based approach may miss optimal routes between discrete grid points
- **Performance**: Grid A* can be slow for large distances
- **Flexibility**: C++ handles irregular spacing; Rust is grid-locked

## 4. VPSC Solver

### C++ Implementation (`vpsc.cpp`, ~1500 lines)

Full **Incremental Constraint Solver** with block-based optimization:

```cpp
class Variable {
    double desiredPosition;
    double finalPosition;
    double weight;
    Block *block;           // Variables grouped in blocks
};

class Block {
    Variables *vars;
    double posn;
    Heap *in, *out;         // Constraint heaps
};

class IncSolver {
    bool satisfy();         // Find feasible solution
    bool solve();           // Optimize within feasibility
    void splitBlocks();     // Split for optimality
    void mergeBlocks();     // Merge for feasibility
};
```

**Algorithm**:
1. Group variables into blocks
2. Iteratively activate most-violated constraints
3. Merge/split blocks as needed
4. Uses Lagrange multipliers for constraint weights

### Rust Implementation (`vpsc.rs`, 558 lines)

Simplified solver without full block optimization:

```rust
pub struct Variable {
    id: usize,
    desired_position: f64,
    final_position: f64,
    weight: f64,
    block_id: Option<usize>,
}

pub struct IncSolver {
    variables: Vec<Variable>,
    constraints: Vec<Constraint>,
    blocks: Vec<Block>,
}
```

### Key Differences

| Aspect | C++ | Rust |
|--------|-----|------|
| Block operations | Full split/merge | Simplified merging only |
| Constraint activation | Heap-based incremental | Iterative pass |
| Lagrange multipliers | Full LM tracking | Not implemented |
| Convergence | Mathematically optimal | Heuristic |

### Impact

- **Optimality**: Rust solver may not find globally optimal solutions
- **Performance**: May require more iterations
- **Stability**: Simpler code, fewer edge cases

## 5. Nudging (Orthogonal Route Improvement)

### C++ Implementation (`orthogonal.cpp`)

```cpp
class NudgingShiftSegment : public ShiftSegment {
    ConnRef *connRef;
    Variable *variable;
    std::vector<size_t> indexes;    // Merged segment indexes
    bool fixed;
    bool finalSegment;
    bool endsInShape;
    bool singleConnectedSegment;
    bool sBend, zBend;
    std::vector<Point> checkpoints;
};
```

**Weight assignment logic** (from lines 183-232):
- `freeWeight (0.00001)`: Zigzag segments
- `strongWeight (0.001)`: C-bends, final segments with checkpoints
- `strongerWeight (1.0)`: Single-segment connectors (bridging shapes)
- `fixedWeight (100000)`: Fixed/immovable segments

**Features**:
- Segment merging for aligned segments
- Checkpoint handling
- `shouldAlignWith()` for segment grouping
- Proper ordering with `fixedOrder()`

### Rust Implementation (`channel.rs`)

```rust
pub enum SegmentType {
    Fixed,      // Checkpoints, constrained
    Final,      // Endpoint segments
    CBend,      // C-shaped bends
    ZigZag,     // Z/S-bends
    Regular,    // Middle segments
}

// Weight constants
const FREE_WEIGHT: f64 = 0.00001;
const STRONG_WEIGHT: f64 = 0.001;
const STRONGER_WEIGHT: f64 = 1.0;
const FIXED_WEIGHT: f64 = 100000.0;
```

### Key Differences

| Aspect | C++ | Rust |
|--------|-----|------|
| Segment merging | Full `mergeWith()` | Not implemented |
| Alignment detection | `shouldAlignWith()`, `canAlignWith()` | Not implemented |
| Checkpoint handling | Full integration | Basic (marks as Fixed) |
| Ordering | `fixedOrder()` with limit checking | Position-based only |
| Channel computation | Proper scanline | Simplified scanline |

### Impact

- **Route Aesthetics**: No segment merging means redundant separation
- **Checkpoint Quality**: Routes through checkpoints less optimized
- **Stability**: Simpler but may produce jitter

## 10. Recommendations

### High Priority (Correctness Issues)

1. **Implement containment map** - Required for correct endpoint routing inside shapes
2. **Add visibility cones** - `inValidRegion()` needed for corner visibility
3. **Fix tie-breaking** - Add timestamp for deterministic routing

### Medium Priority (Route Quality)

1. **Segment merging** - Implement `shouldAlignWith()` / `mergeWith()`
2. **Default bend penalty** - Consider matching C++ default (0.0)
3. **Improve orthogonal visibility graph** - Replace grid-based approach

### Lower Priority (Performance/Features)

1. **Block allocator** - For high-volume routing scenarios
2. **Progress callbacks** - For large transaction responsiveness
3. **Full VPSC solver** - Block split/merge for optimality

## Conclusion

The Rust port successfully captures the **core architecture and algorithms** of libavoid but represents a **simplification rather than a 1:1 port**. The most significant algorithmic differences are:

1. **Visibility computation**: Missing containment and visibility cones
2. **Orthogonal routing**: Grid-based vs visibility graph approach
3. **VPSC solver**: No block splitting for optimality
4. **Nudging**: No segment merging or alignment detection

For typical diagram routing use cases, the Rust implementation should produce **functional routes** but may differ in:
- Edge cases near shape corners
- Aesthetic quality of complex routes
- Performance on large graphs

The implementation is suitable for **production use** with awareness of these limitations. For applications requiring exact parity with libavoid C++, the identified gaps should be addressed.
