# Parity Audit: libavoid C++ vs Rust Implementation

**Date:** 2024-11-24
**Audit Scope:** Full algorithmic comparison between C++ libavoid and Rust port
**Purpose:** Identify meaningful differences, particularly algorithmic, between implementations

## Executive Summary

This audit reveals **critical algorithmic differences** between the C++ and Rust implementations that significantly affect routing behavior. The most severe issues are:

1. **10x difference in default SegmentPenalty** (1.0 vs 10.0) - directly impacts orthogonal routing quality
2. **Missing weight stratification** in VPSC nudging - eliminates distinction between different segment types
3. **Transaction mode defaults inverted** (false vs true) - affects batching behavior
4. **Simplified orthogonal routing** - missing scanline-based channel building for obstacle avoidance
5. **Missing routing options** - several C++ routing options not implemented

These differences will cause the Rust implementation to produce materially different routing results, especially for orthogonal routing with nudging enabled.

## 1. Router Initialization & Configuration

### 1.1 Default Parameters

#### CRITICAL DIFFERENCE: SegmentPenalty Default

**C++ (`router.cpp:89`):**
```cpp
m_routing_parameters[segmentPenalty] = 10;
```

**Rust (`router.rs:154`):**
```rust
router.parameters.insert(RoutingParameter::SegmentPenalty, 1.0);
```

**Impact:** 10x difference. The C++ implementation uses `segmentPenalty = 10` which is critical for proper orthogonal routing. With the Rust default of 1.0, routes will prefer more segments over distance minimization, producing suboptimal results.

**Severity:** HIGH - This fundamentally changes routing cost calculations.

## 2. Orthogonal Routing Algorithms

### 2.1 Visibility Graph Generation

#### Both implementations use scanline sweep

**C++ Approach (`orthogonal.cpp`, `scanline.cpp`):**
- Two-pass scanline sweep (vertical then horizontal)
- Event-driven processing with Open/Close/ConnPoint events
- Line segment merging with breakpoint generation
- Generates static orthogonal visibility graph

**Rust Approach (`orthogonal_visgraph.rs`):**
- Two-pass scanline sweep (vertical then horizontal)
- Event-driven processing with ShapeOpen/ShapeClose/ConnPoint events
- Segment list management with PosVertInf breakpoints
- Generates visibility graph edges

**Verdict:** ✅ **ALGORITHMICALLY EQUIVALENT** - Both use the same fundamental algorithm with minor implementation differences.

---

### 2.2 Segment Nudging - Channel Building

#### CRITICAL DIFFERENCE: Channel Information

**C++ (`scanline.cpp:462` - `buildOrthogonalChannelInfo`):**
- Performs a **scanline sweep to determine space for shifting segments**
- Creates events for obstacles and segments
- Processes in multiple passes (4 passes) to build channel limits
- Sets `minSpaceLimit` and `maxSpaceLimit` for each segment based on nearby obstacles
- Uses `processShiftEvent()` to update scanline and segment limits

**Rust (`channel.rs:240` - `build_shift_segments_with_obstacles`):**
- Uses a **simplified bounding-box approach**
- Iterates through obstacles and checks overlap in parallel dimension
- If overlap detected, constrains segment limits
- **Does NOT use scanline sweep** - O(n×m) instead of O((n+m) log(n+m))

**Code Comparison:**

C++ (scanline.cpp:471-558):
```cpp
// Do a sweep to determine space for shifting segments.
size_t altDim = (dim + 1) % 2;
const size_t n = router->m_obstacles.size();
const size_t cpn = segmentList.size();
size_t totalEvents = 2 * (n + cpn);
Event **events = new Event*[totalEvents];
// ... builds events for obstacles and segments
qsort((Event*)events, (size_t) totalEvents, sizeof(Event*), compare_events);
// Process the sweep with multiple passes
for (int pass = 2; pass <= 4; ++pass) {
    for (unsigned j = posStartIndex; j < posFinishIndex; ++j) {
        processShiftEvent(scanline, events[j], dim, pass);
    }
}
```

Rust (channel.rs:240-313):
```rust
// Simple bounding box approach
for obstacle in obstacles {
    let obs_bbox = obstacle.bounding_box();
    // ... check if segment overlaps obstacle in parallel dimension
    if seg_range_min < obs_par_max && seg_range_max > obs_par_min {
        // Constrain limits
        if seg_pos < obs_perp_min {
            new_max_limit = new_max_limit.min(obs_perp_min - nudge_distance);
        } else if seg_pos > obs_perp_max {
            new_min_limit = new_min_limit.max(obs_perp_max + nudge_distance);
        }
    }
}
```

**Impact:**
1. **Algorithmic complexity:** C++ is O((n+m) log(n+m)), Rust is O(n×m)
2. **Accuracy:** C++ finds nearest obstacles in both directions via scanline, Rust may miss complex obstacle configurations
3. **Channel information:** C++ computes precise available space, Rust uses simplified constraints

**Severity:** HIGH - This is a fundamental algorithmic difference that affects routing quality in complex scenarios.

### 2.3 VPSC Nudging Weights

#### CRITICAL DIFFERENCE: Weight Stratification

**C++ (`orthogonal.cpp:58-61`):**
```cpp
static const double freeWeight   = 0.00001;
static const double strongWeight = 0.001;
static const double strongerWeight = 1.0;
static const double fixedWeight  = 100000;
```

The C++ implementation uses **four weight levels** to control segment behavior:
- `freeWeight`: Middle segments that can move freely
- `strongWeight`: C-bend segments that prefer their position
- `strongerWeight`: Single-segment connectors that strongly prefer their position
- `fixedWeight`: Endpoint segments that must stay fixed

**Rust (`channel.rs:16-18`):**
```rust
const FREE_WEIGHT: f64 = 0.00001;
const FIXED_WEIGHT: f64 = 100000.0;
```

The Rust implementation uses **only two weight levels**:
- `FREE_WEIGHT`: All movable segments
- `FIXED_WEIGHT`: Fixed segments

**Impact:** The Rust implementation treats all movable segments equally, losing the distinction between:
1. **C-bends** (which should resist movement)
2. **Z-bends** (which can move freely)
3. **Single-segment routes** (which should strongly maintain position)
4. **Final segments** (optionally nudged with strong weight)

This results in **less stable nudging** where segments that should hold their ground may move excessively.

**Severity:** HIGH - Significantly affects nudging quality and route stability.

---

### 2.4 Segment Classification

**C++ (`orthogonal.cpp`):**
Classifies segments into:
- **Fixed segments:** Checkpoint segments, optionally final segments
- **Final segments:** Segments adjacent to endpoints
- **Zigzag segments:** S-bends and Z-bends (free to move)
- **C-bend segments:** C-shaped bends (strong resistance)
- **Regular segments:** Other middle segments

**Rust (`channel.rs`):**
Classifies segments into:
- **Fixed segments:** Endpoint segments (low_idx == 0 or high_idx == len-1)
- **Free segments:** All other segments

**Impact:** Missing the C-bend vs zigzag distinction means suboptimal nudging behavior.

**Severity:** MEDIUM - Affects aesthetic quality of routes.

## 3. Visibility Graph Construction

### 3.1 Visibility Computation Algorithms

#### Both implementations use similar approaches

**C++ (`visibility.cpp`):**
- `computeVisibilityNaive()`: O(n²) pairwise visibility checks
- `computeVisibilitySweep()`: Lee's rotational sweep algorithm O(n² log n)
- Edge visibility testing via `EdgeInf::checkEdgeVisibility()`

**Rust (`visibility.rs`):**
- `compute_vertex_visibility()`: O(n²) pairwise visibility checks
- `compute_vertex_visibility_sweep()`: Lee's sweep (partially implemented)
- Edge visibility via `is_visible()` with segment intersection tests

**Verdict:** ✅ **ALGORITHMICALLY EQUIVALENT** - Both use the same fundamental visibility algorithms. The Rust sweep implementation is noted as not fully implemented but the naive approach is complete.

---

### 3.2 Incremental Updates

**C++ (`router.cpp`):**
- `processActions()`: Removes/restores obstacles, updates visibility incrementally
- Checks blocked/unblocked edges
- Recalculates visibility only for moved obstacles

**Rust (`router.rs`):**
- `update_visibility_graph()`: Marks dirty shapes, updates within "visibility margin"
- Falls back to full rebuild if >50% shapes dirty
- Default visibility margin: 1000.0 units

**Verdict:** ✅ **SIMILAR APPROACH** - Both use incremental updates with different thresholds and heuristics.

## 4. Path Finding & Cost Functions

### 4.1 A* Implementation

#### Both use standard A* with similar heuristics

**C++ (`makepath.cpp`):**
- ANode structure with g/h/f scores
- Priority queue ordered by f-score
- Heuristic: Euclidean distance (polyline) or Manhattan distance (orthogonal)
- Tie-breaking via timestamps

**Rust (`graph.rs`):**
- PathVertex with g_score/f_score
- BinaryHeap ordered by f-score
- Heuristic: Euclidean distance scaled by `heuristic_weight`
- Generation counter for state reuse

**Verdict:** ✅ **ALGORITHMICALLY EQUIVALENT** - Standard A* implementations.

---

### 4.2 Cost Function Differences

#### Edge cost penalties differ in detail

**C++ (`makepath.cpp` - `cost()` function):**
- Base distance (Euclidean or Manhattan)
- Angle penalty using **logarithmic scale**: `penalty * log10(angle/π)`
- Segment penalty for non-collinear segments
- Cluster crossing penalty
- Reverse direction penalty (moving away from target)
- Crossing penalty (post-processing)
- Shared path penalty

**Rust (`graph.rs` - `find_path_with_result()`):**
- Base distance
- Angle penalty using **linear scale**: `penalty * (angle / π)`
- Segment penalty per edge
- Reverse penalty: `min((dist_after - dist_before) / dist_before, 1.0)`
- Crossing penalty (if edges are shared)

**Key Difference:**

C++ uses **logarithmic angle penalty**:
```cpp
cost += angleWeight * std::log10(1.0 + (angle / M_PI));
```

Rust uses **linear angle penalty**:
```rust
cost += angle_penalty * (angle / std::f64::consts::PI);
```

**Impact:** The logarithmic scaling in C++ gives less penalty to moderate turns (45-90°) and more penalty to sharp turns (>135°). The linear scaling in Rust penalizes all turns proportionally to the angle.

**Severity:** MEDIUM - Affects path aesthetics and turn preferences, but not fundamental correctness.

## 5. VPSC Constraint Solver

### 5.1 Core Algorithm

#### Both implement the same VPSC algorithm

**C++ (`vpsc.cpp` - `IncSolver`):**
- Variables grouped into Blocks
- Iterative constraint satisfaction via `solve()`
- Block merging on violated constraints
- Block splitting on negative Lagrange multipliers
- Position optimization via weighted averages

**Rust (`vpsc.rs` - `IncSolver`):**
- Variables grouped into Blocks
- Iterative solving via `solve()`
- Block merging via `merge()`
- Position calculation via `PositionStats`
- Same mathematical formulation

**Verdict:** ✅ **ALGORITHMICALLY EQUIVALENT** - Both correctly implement VPSC from Dwyer et al. 2005.

---

### 5.2 Implementation Details

**Minor differences:**
- C++ uses `list<Block*>`, Rust uses `Vec<Block>`
- C++ uses `set<Constraint*>` for active constraints, Rust uses `Vec<Constraint>`
- Same convergence criteria and handling of unsatisfiable constraints

**Verdict:** ✅ Implementation differences are stylistic, not algorithmic.

## 6. Transaction & Batching

### 6.1 Action Queue Processing

**C++ (`router.cpp` - `processTransaction()`):**
1. Process action list (sorted by type)
2. Remove affected obstacles from graph
3. Mark connectors for reroute
4. Update visibility edges
5. Restore obstacles with new positions
6. Reroute connectors
7. Improve routes (nudging, hyperedges)

**Rust (`router.rs` - `process_transaction()`):**
1. Process action queue (FIFO order)
2. Rebuild visibility graph if needed
3. Process reroute queue
4. Apply nudging if enabled

**Differences:**
- C++ uses sorted action processing, Rust uses FIFO
- C++ does incremental visibility edge updates, Rust does full rebuild when needed
- C++ has more sophisticated action types (ConnChange, JunctionMove, etc.)

**Verdict:** ⚠️ **DIFFERENT STRATEGY** - C++ is more incremental, Rust is more coarse-grained. Both are correct but have different performance characteristics.

## 9. Summary of Critical Differences

### High Severity (Affect Routing Correctness)

1. **SegmentPenalty Default: 1.0 vs 10.0**
   - Location: `router.rs:154` vs `router.cpp:89`
   - Impact: 10x difference fundamentally changes routing costs
   - Fix: Change Rust default to 10.0

2. **Missing VPSC Weight Stratification**
   - Location: `channel.rs:16-18` (missing strongWeight, strongerWeight)
   - Impact: All movable segments treated equally, losing C-bend resistance
   - Fix: Implement 4-tier weight system with segment classification

3. **Simplified Channel Building**
   - Location: `channel.rs:240` (missing scanline sweep)
   - Impact: Less accurate obstacle avoidance, O(n×m) complexity
   - Fix: Port `buildOrthogonalChannelInfo` scanline algorithm

### Medium Severity (Affect Quality/Performance)

4. **Transaction Mode Default Inverted**
   - Location: `router.rs:140` (false vs true)
   - Impact: Performance and update behavior differ from C++
   - Fix: Change default to true for consistency

5. **Linear vs Logarithmic Angle Penalty**
   - Location: `graph.rs` (linear) vs `makepath.cpp` (logarithmic)
   - Impact: Different turn preferences
   - Fix: Implement logarithmic scaling

6. **Missing Routing Options**
   - Location: `router.rs:162-165` (missing 5 options)
   - Impact: Less configurability
   - Fix: Add missing options

7. **Hyperedge Routing Not Implemented**
   - Location: `hyperedge.rs` (stubs only)
   - Impact: Multi-terminal routing unavailable
   - Fix: Port hyperedge improver and rerouter

### Low Severity (Cosmetic/Advanced Features)

8. **BendPenalty and ShapeBufferDistance Defaults**
   - Different defaults but user-configurable
   - Impact: Minor path selection differences

9. **Cluster Support Missing**
   - Advanced feature, rarely used

## 10. Recommendations

### Immediate Fixes (Critical for Parity)

1. **Change SegmentPenalty default to 10.0** in `router.rs:154`
2. **Implement 4-tier weight system** in `channel.rs`:
   - Add `STRONG_WEIGHT = 0.001` and `STRONGER_WEIGHT = 1.0`
   - Classify segments (C-bend, zigzag, final, regular)
   - Apply appropriate weights in VPSC problem

3. **Port scanline-based channel building** from `scanline.cpp`:
   - Implement `build_orthogonal_channel_info()` with event-driven sweep
   - Replace simplified bounding-box approach
   - This is the most complex fix but necessary for quality parity

### High Priority (For Quality Parity)

4. **Change transaction_mode default to true** for consistency
5. **Implement logarithmic angle penalty** in pathfinding
6. **Add missing routing options** for configurability

### Medium Priority (For Feature Completeness)

7. **Complete hyperedge routing implementation**
8. **Implement pin visibility computation**
9. **Add cluster support**

### Testing Recommendations

After fixes, verify parity with:
- Test cases from C++ libavoid test suite
- Visual comparison of routing results
- Performance benchmarks
- Nudging quality assessment (overlapping routes should separate cleanly)

---

## 11. Conclusion

The Rust port has successfully replicated the core algorithms (visibility graphs, A* pathfinding, VPSC solver) but has **three critical differences** that prevent routing parity:

1. Wrong default SegmentPenalty (off by 10x)
2. Oversimplified VPSC weight system (missing 2 tiers)
3. Missing scanline-based channel building (simplified to O(n×m) approach)

These differences will cause **materially different routing behavior**, especially in complex scenarios with orthogonal routing and nudging enabled. The recommended fixes are clear but require moderate implementation effort, particularly for the scanline channel building.

**Bottom Line:** The Rust implementation is a good foundation but is not yet at parity with C++ libavoid. The three critical fixes above are necessary to achieve equivalent routing quality.
