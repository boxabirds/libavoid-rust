## 1. Critical Bug: `moveShape` API Mismatch

### Problem

The WASM `moveShape` binding has incorrect parameter semantics:

**libavoid-js (C++ original):**
```typescript
moveShape(shape: ShapeRef, xDiff: number, yDiff: number);  // OFFSETS
moveShape(shape: ShapeRef, newPolygon: Polygon);          // New position
```

**libavoid-rust WASM:**
```rust
// src/wasm.rs:658-660
pub fn move_shape(&mut self, shape: &ShapeRef, x: f64, y: f64) {
    self.inner.move_shape(shape.id(), RustPoint::new(x, y));  // Treats as ABSOLUTE
}
```

### Impact

When calling `router.moveShape(shape, 30, 20)`:
- **Expected:** Move shape BY offset (30, 20) from current position
- **Actual:** Move shape TO absolute position (30, 20)

This breaks the Shape Operations gallery example and any code relying on relative movement.

### Fix Required

Change WASM binding to match libavoid-js semantics:

```rust
#[wasm_bindgen(js_name = moveShape)]
pub fn move_shape(&mut self, shape: &ShapeRef, x_diff: f64, y_diff: f64) {
    // Get current position and add offset
    if let Some(shape_ref) = self.inner.get_shape(shape.id()) {
        let current = shape_ref.position();
        let new_pos = RustPoint::new(current.x + x_diff, current.y + y_diff);
        self.inner.move_shape(shape.id(), new_pos);
    }
}
```

## 2. Fixed Bug: Visibility Graph One-Directional Edges

### Problem (Now Fixed)

The visibility graph was creating edges only in one direction. When computing visibility for src/dst vertices:
- Edges were added FROM src TO obstacle corners
- But NOT from corners TO dst

A* pathfinding needs edges traversable from src → corners → dst.

### Fix Applied

Modified `visibility.rs:compute_vertex_visibility()` to add bidirectional edges.
